# How Test Macros Expand into Class Declarations

This note explains how macro dispatch works in `gcheck`, starting from `TEST(...)`, then showing how the same mechanism produces template class declarations for function-style tests.

## 1. Core Dispatcher: `VFUNC`

From `include/macrotools.h`:

```cpp
#define __HEAD(head, ...) head
#define __TAIL(head, ...) __VA_ARGS__

#define __NARG__(...)  __NARG_I_(__VA_ARGS__,__RSEQ_N())
#define __NARG_I_(...) __ARG_N(__VA_ARGS__)
#define __ARG_N( _1, _2, _3, _4, _5, _6, _7, _8, N, ...) N
#define __RSEQ_N() 8,7,6,5,4,3,2,1,0

#define _VFUNC_(name, n) name##n
#define _VFUNC(name, n) _VFUNC_(name, n)
#define VFUNC(func, ...) _VFUNC(func, __NARG__(__VA_ARGS__))(__VA_ARGS__)
```

`VFUNC` does two things:

1. Counts how many arguments were passed.
2. Concatenates that count to a macro base name.

Example:

```cpp
VFUNC(_TEST, A, B)      -> _TEST2(A, B)
VFUNC(_TEST, A, B, C)   -> _TEST3(A, B, C)
VFUNC(_IOTEST, ...)     -> _IOTEST4(...) or _IOTEST5(...) etc.
```

## 1.1 How `macrotools.h` Macros Work

`macrotools.h` has four groups of helpers.

### A) Variadic list splitters

```cpp
#define __HEAD(head, ...) head
#define __TAIL(head, ...) __VA_ARGS__
```

1. `__HEAD(a, b, c)` expands to `a`.
2. `__TAIL(a, b, c)` expands to `b, c`.

These are used in test macros where:

1. The first variadic argument is usually the callable under test.
2. The rest are optional metadata (points, prerequisites).

### B) Argument counting (`__NARG__`)

```cpp
#define __NARG__(...)  __NARG_I_(__VA_ARGS__,__RSEQ_N())
#define __NARG_I_(...) __ARG_N(__VA_ARGS__)
#define __ARG_N( _1, _2, _3, _4, _5, _6, _7, _8, N, ...) N
#define __RSEQ_N() 8,7,6,5,4,3,2,1,0
```

Step-by-step example for 4 args:

1. `__NARG__(A, B, C, D)`
2. `-> __NARG_I_(A, B, C, D, 8,7,6,5,4,3,2,1,0)`
3. `-> __ARG_N(A, B, C, D, 8,7,6,5,4,3,2,1,0)`
4. `N` lands on `4`
5. Result: `4`

So this macro family computes the arity (up to 8 args).

### C) Token pasting for overload name construction

```cpp
#define _VFUNC_(name, n) name##n
#define _VFUNC(name, n) _VFUNC_(name, n)
```

1. `_VFUNC(_TEST, 2)` -> `_VFUNC_(_TEST, 2)` -> `_TEST2`.
2. The two-level form forces `n` to fully expand before token pasting.

### D) Final dispatcher

```cpp
#define VFUNC(func, ...) _VFUNC(func, __NARG__(__VA_ARGS__))(__VA_ARGS__)
```

Example:

1. `VFUNC(_TEST, Suite, Case)`  
2. `__NARG__(Suite, Case)` -> `2`  
3. `_VFUNC(_TEST, 2)` -> `_TEST2`  
4. Final call: `_TEST2(Suite, Case)`

This is how `TEST`, `FUNCTIONTEST`, `IOTEST`, and `METHODTEST` all select the correct internal macro by argument count.

## 2. Starting Point: `TEST(...)`

From `include/customtest.h`:

```cpp
#define TEST(...) \
    VFUNC(_TEST, __VA_ARGS__)
```

Supported forms route like this:

1. `TEST(suite, test)` -> `_TEST2`
2. `TEST(suite, test, points)` -> `_TEST3` -> `_TEST4` -> `_TEST5`
3. `TEST(suite, test, points, prereqs)` -> `_TEST4` -> `_TEST5`
4. `TEST(suite, test, points, prereqs, timeout)` -> `_TEST5`

The key definition:

```cpp
#define _TEST5(suitename, testname, points, prerequisites, timeoutval) \
    class GCHECK_TEST_##suitename##_##testname : public gcheck::CustomTest { \
        void TheTest(); \
    public: \
        GCHECK_TEST_##suitename##_##testname() : CustomTest(gcheck::TestInfo(#suitename, #testname, points, prerequisites)) { timeout_ = timeoutval; } \
    }; \
    GCHECK_TEST_##suitename##_##testname GCHECK_TESTVAR_##suitename##_##testname; \
    void GCHECK_TEST_##suitename##_##testname::TheTest()
```

Important detail: `TEST(...)` generates a concrete class, not a template class. It is for `CustomTest` style tests.

## 3. Where Template Classes Are Generated

Template class declarations are generated by `FUNCTIONTEST`, `IOTEST`, and `METHODTEST`.

### 3.1 `FUNCTIONTEST(...)`

From `include/function_test.h`:

```cpp
#define FUNCTIONTEST(...) \
    VFUNC(_FUNCTIONTEST, __VA_ARGS__)
```

`VFUNC` selects `_FUNCTIONTEST4` or `_FUNCTIONTEST5` (with 6/7 forwarding to 5), and those macros declare:

```cpp
template<typename ReturnT, typename... Args>
class GCHECK_TEST_<suite>_<test> : public gcheck::FunctionTest<ReturnT, Args...> { ... };
```

Then they instantiate:

```cpp
GCHECK_TEST_<suite>_<test> GCHECK_TESTVAR_<suite>_<test>(<function>);
```

and open:

```cpp
template<typename ReturnT, typename... Args>
void GCHECK_TEST_<suite>_<test><ReturnT, Args...>::SetInputsAndOutputs()
```

### 3.2 `IOTEST(...)`

From `include/io_test.h`:

```cpp
#define IOTEST(...) \
    VFUNC(_IOTEST, __VA_ARGS__)
```

`VFUNC` selects `_IOTEST4` or `_IOTEST5` (6/7 forward to 5). These declare:

```cpp
template<typename ReturnT, typename... Args>
class GCHECK_TEST_<suite>_<test> : public gcheck::IOTest<ReturnT, Args...> { ... };
```

### 3.3 `METHODTEST(...)`

From `include/method_test.h`:

```cpp
#define METHODTEST(...) \
    VFUNC(_METHODTEST, __VA_ARGS__)
```

`VFUNC` selects `_METHODTEST4` or `_METHODTEST5` (6/7 forward to 5). These declare:

```cpp
template<typename ReturnT, typename ObjectType, typename... Args>
class GCHECK_TEST_<suite>_<test> : public gcheck::MethodTest<ReturnT, ObjectType, Args...> { ... };
```

## 4. Why `__HEAD` and `__TAIL` Exist

In the `*5` forms, arguments after the required ones are split:

1. `__HEAD(__VA_ARGS__)` picks the first variadic argument (the callable under test).
2. `__TAIL(__VA_ARGS__)` passes remaining optional metadata (points, prerequisites) into `TestInfo(...)`.

That lets one macro support both:

1. Required callable binding.
2. Optional scoring/prerequisite parameters.

## 5. One Concrete Expansion Example

Input:

```cpp
IOTEST(Math, AddIO, 3, add, 5, "Warmup.Basic")
{
    // body
}
```

Dispatch path:

1. `IOTEST(...)`
2. `VFUNC(_IOTEST, ...)`
3. `_IOTEST6(...)`
4. `_IOTEST5(...)`

Result shape:

```cpp
template<typename ReturnT, typename... Args>
class GCHECK_TEST_Math_AddIO : public gcheck::IOTest<ReturnT, Args...> { ... };

GCHECK_TEST_Math_AddIO GCHECK_TESTVAR_Math_AddIO(add);

template<typename ReturnT, typename... Args>
void GCHECK_TEST_Math_AddIO<ReturnT, Args...>::SetInputsAndOutputs()
{
    // body
}
```

This is the same expansion pattern used by the other function-style test macros.

## 6. Equivalence to a Modern Template-Based Design

If you remove macro arity dispatch and use modern C++ registration, the runtime model can stay the same: each test is still its own class, and all tests are still auto-collected into a global registry.

### 6.1 One-to-One Mapping

Current macro-generated pieces map to modern constructs like this:

1. `class GCHECK_TEST_<suite>_<test> : public ...`  
   -> You write a normal named class directly.
2. `GCHECK_TESTVAR_<suite>_<test>` global instance for registration  
   -> `inline static` registrar (`AutoRegister<T>`) that adds a factory to `Registry`.
3. `TestInfo(#suite, #test, points, prereqs)`  
   -> `static constexpr`/`static const` metadata field on the class.
4. Macro-opened method body (`TheTest()` or `SetInputsAndOutputs()`)  
   -> Ordinary virtual override or regular member function.
5. `Test::RunTests()` iterating static list  
   -> Runner iterates `Registry::factories()` and executes constructed tests.

So equivalence is behavioral, not textual: macro code-generation is replaced by explicit typed code that represents the same objects and flow.

### 6.2 Side-by-Side Shape

Macro style (`TEST`/`IOTEST` family) effectively produces:

```cpp
class GeneratedTest : public BaseTestType { ... };
GeneratedTest generated_instance;  // static registration side effect
void GeneratedTest::TestBody() { ... }
```

Modern typed style can be:

```cpp
class MyTest : public BaseTestType, private AutoRegister<MyTest> {
public:
    static const TestInfo kInfo;
    void TestBody() override { ... } // or SetInputsAndOutputs()
};
```

Both approaches still have:

1. A unique class per test.
2. Static-time registration into a global collection.
3. Metadata (`suite`, `test`, `points`, `prereqs`) attached to that test.
4. A runner that loops over collected tests and executes them.

### 6.3 What Actually Changes

1. Argument-count macro dispatch (`VFUNC`, `_TEST2/_TEST5`, etc.) is removed.
2. Type selection moves from preprocessor tricks to templates/overloads/concepts.
3. Errors become normal C++ diagnostics instead of preprocessor expansion failures.

This is why the designs are equivalent in behavior while different in implementation mechanics.
